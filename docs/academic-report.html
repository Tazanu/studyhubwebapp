Abstract

University students routinely hold the knowledge their peers need, yet that knowledge stays trapped in private messaging groups, personal hard drives and individual notebooks. A student who misses a lecture, is stuck on a problem set, or needs one-to-one help on a single topic has no dependable place to look. Existing alternatives each solve part of the problem and none of it well: institutional learning management systems distribute material downwards from lecturers but carry no peer-to-peer channel; global question-and-answer sites are strong on programming and weak on local curricula; commercial tutoring marketplaces price in foreign currency and settle by card, which excludes most students in Cameroon, where payment is overwhelmingly by mobile money.

This project designed, implemented and deployed StudyHub, a full-stack web application that consolidates four functions into a single authenticated platform: subject-based study groups with real-time messaging, a shared repository of course notes, a question-and-answer forum with voting and accepted answers, and a peer-tutoring marketplace with booking and payment. Payment is handled natively through MTN Mobile Money and Orange Money, the two instruments students actually hold.

The system was built as two independently deployed tiers. The client is a React 19 single-page application, installable as a Progressive Web Application and usable on a degraded network; the server is an Express 5 REST API backed by PostgreSQL through the Prisma ORM, with a Socket.IO channel for real-time messaging. The implementation comprises approximately 20,700 lines of source across 88 REST endpoints and a 25-table relational schema, and is deployed live on a three-service free-tier infrastructure.

Particular engineering attention was paid to three areas where the operating context imposed constraints a textbook design does not anticipate. First, payment integrity: mobile money settlement is asynchronous and unreliable, so the system resolves all prices server-side, grants entitlements idempotently, and runs a background reconciler that guarantees a successful charge eventually grants access even if the payer closes the browser. Second, content protection: paid material is stored under authenticated delivery and released only through a signed, expiring URL issued after an entitlement check, while free material is redirected to a CDN — a change that reduced a 3.19 MB download from a 300-second timeout to 31 seconds on the same connection. Third, usability under constraint: the client tolerates a sleeping free-tier backend by retrying only transport-level failures, and the interface is fully bilingual in English and French, with 1,228 verified translation keys per language.

The system was verified through static analysis, production build validation, an automated locale-consistency checker, and structured manual testing across both languages and both colour themes. The work delivers a functioning, publicly deployed platform; it does not include an automated regression test suite or a formal user evaluation, and both are identified as the principal directions for further work.

Keywords: collaborative learning; peer-to-peer education; web application; React; Node.js; PostgreSQL; mobile money; Progressive Web Application; real-time communication; internationalisation; Cameroon.

Chapter One

Introduction

1.1  Background of the study

Higher education depends on more than the formal transmission of material from lecturer to student. A substantial part of what a student learns is acquired laterally: from a classmate who has already understood a derivation, from a set of notes taken in a lecture one happened to miss, from an argument worked through with peers the evening before an assessment. This lateral channel is well documented in the education literature as peer-assisted learning, and it is largely informal.

In practice, the informality is the problem. At a typical Cameroonian university the channel exists almost entirely inside private WhatsApp groups, personal laptops and paper notebooks. Material circulates, but it circulates within closed circles, disappears when a group is archived, and is undiscoverable by anyone outside it. A student in the same department, taking the same course, may have no route to a resource that another student produced a week earlier.

Two further constraints shape the local context. Bandwidth is expensive and intermittent, which makes heavyweight platforms impractical and makes any design that assumes a stable connection fragile in use. Payment is overwhelmingly by mobile money rather than by card, so any system that intends to move money between students must settle through MTN Mobile Money or Orange Money; a card-only checkout excludes the intended users almost entirely.

1.2  Statement of the problem

There is no single, accessible, locally appropriate platform on which university students can share academic resources, resolve specific academic difficulties, and obtain paid one-to-one help from their peers. The absence manifests in four concrete ways:

  1. Knowledge is siloed. Notes and explanations exist but are trapped in private channels and personal storage, so they benefit a handful of people rather than a cohort.
  2. Help is unreliable and untracked. A question asked in a chat group scrolls out of view within hours. There is no record of which answer was correct, no accumulation of a searchable body of resolved problems, and no incentive for the person who answered.
  3. Tutoring is informal and unsafe. Peer tutoring is arranged by word of mouth with no verification of competence, no agreed rate, no schedule and no payment record, which exposes both parties.
  4. Existing platforms do not fit. International alternatives assume card payment, foreign currency pricing, generous bandwidth and a curriculum that is not the local one.

1.3  Aim and objectives

Aim. To design, implement and deploy a secure, accessible web-based platform that consolidates peer-to-peer academic collaboration and paid peer tutoring for university students, using payment instruments appropriate to the local context.

1.4  Research questions

  1. What functions must a peer-to-peer academic platform provide in order to displace the informal channels students currently rely upon?
  2. How can an asynchronous, failure-prone mobile money settlement process be integrated such that entitlement is granted exactly once and never lost?
  3. How can purchased digital content be protected from unauthorised access while remaining inexpensive to deliver at scale?
  4. What design measures allow a web application on free-tier infrastructure to remain usable over an intermittent connection?

1.5  Scope and delimitation

In scope. A responsive web application, installable as a Progressive Web Application, covering: account management with role-based access; study groups with real-time chat; upload, discovery and download of course notes, both free and paid; a question-and-answer forum with voting, accepted answers and reputation; a tutor directory with applications, administrative review, availability and booking; mobile money payment with receipts; an administrative console; and a bilingual interface.

Out of scope. Native mobile applications for Android or iOS; video conferencing within the platform (sessions are arranged, not hosted); automated assessment or grading; integration with any university's existing student information system; and card or bank payment instruments.

1.6  Significance of the study

For students, the platform converts a scattered informal practice into a durable, searchable resource, and makes it possible to obtain targeted help without a prior social connection to the person able to give it. For those who tutor, it creates a verifiable record of competence and a payment mechanism they can actually use, turning unpaid favours into modest income. Methodologically, the project contributes a documented treatment of two problems under-addressed in general web-development literature: reliable entitlement granting over an asynchronous mobile money rail, and delivery of protected digital goods on constrained infrastructure.

Chapter Two

Literature Review and Related Work

2.1  Theoretical basis: peer-assisted learning

The pedagogical premise of this project is that students learn effectively from one another. Two established ideas support it. Vygotsky's notion of the zone of proximal development holds that a learner progresses furthest when assisted by someone whose understanding is only modestly ahead of their own — a description that fits a classmate more closely than it fits a lecturer. Constructivist accounts of learning further hold that knowledge is built by the learner rather than transferred intact, which implies that the act of explaining a concept benefits the explainer as much as the recipient.

Both ideas argue for a system that is symmetric: every participant is simultaneously a potential consumer and a potential producer of help. This principle shaped the design directly. There is no separate class of "content provider"; any student may upload notes, answer questions, or apply to tutor, and the reputation mechanism rewards contribution rather than consumption.

2.2  Review of existing systems

2.2.1  Institutional learning management systems

Platforms such as Moodle and Google Classroom are the standard vehicle for course administration. Their orientation is vertical: a lecturer publishes, students receive. Where discussion features exist they are typically per-course forums with weak discovery and no reputation. They are also institution-bound — a student cannot obtain help from a peer at another university, or in a subject outside their enrolled courses — and self-hosted deployments impose an administrative burden the students themselves cannot discharge.

2.2.2  General question-and-answer platforms

Stack Overflow and the wider Stack Exchange network demonstrate convincingly that voting, accepted answers and reputation produce a durable, searchable knowledge base. The mechanism is sound and this project adopts it. The limitation is coverage: these platforms are strongest in software engineering, apply strict topicality rules that exclude coursework-style questions, and hold essentially nothing specific to a Cameroonian curriculum. They also offer no mechanism for arranging sustained one-to-one help.

2.2.3  Commercial note-sharing services

Course Hero and Studocu aggregate student-generated study material at scale and confirm demand. Two characteristics make them unsuitable here. Pricing is in foreign currency with card settlement, which excludes the target users on payment grounds alone. More fundamentally, their economics reward volume of uploads rather than quality, and the resulting quality variance is a known criticism; this project responds with an explicit quality gate and human review for paid material (Section 5.5).

2.2.4  Online tutoring marketplaces

Preply, Wyzant and comparable services implement the marketplace pattern this project adopts for tutoring: profiles, verification, scheduling, booking and payment. They are designed for cross-border tutoring at international rates, settle by card, and take a substantial commission. None operates meaningfully in the Cameroonian student market at student-affordable rates.

2.2.5  Informal messaging groups

The incumbent, and the system any replacement must actually beat, is WhatsApp. Its advantages are decisive: universal adoption, negligible data cost, and zero onboarding friction. Its deficiencies are equally clear. Content is ephemeral and unsearchable; a question scrolls away within hours; files are lost when a device is replaced; there is no notion of a correct answer; membership is by invitation, so discovery is impossible; and there is no payment or accountability mechanism for tutoring.

2.4  Identified gap

No reviewed system combines all six capabilities. The strongest individual mechanisms are well proven and are deliberately reused: the reputation and accepted-answer model from Stack Exchange, and the profile-schedule-book-pay marketplace pattern from the tutoring services. What is absent is their integration into one platform, settled through mobile money and engineered for an intermittent connection. That integration is the contribution of this work.

Design consequence

Because the incumbent is WhatsApp rather than a competing web platform, the design is judged against a low-friction, near-zero-cost baseline. This drove three decisions: the application is installable and works partly offline so it behaves like a native app; the first load is optimised and a sleeping backend is handled gracefully rather than surfacing as an error; and group chat is real-time, since a slower-than-WhatsApp chat would not be adopted regardless of its other merits.

Methodology

3.1  Development methodology

An iterative and incremental methodology was adopted in preference to a sequential waterfall approach. The justification is that several requirements — particularly the behaviour of the mobile money provider under failure — could not be specified accurately in advance and were only discovered by building against the live service. A methodology that fixed the specification before implementation would have fixed it wrongly.

3.2  Requirements elicitation

Requirements were derived from three sources: observation of how students currently exchange academic material in informal channels; the feature analysis of comparable systems presented in Chapter Two, which established both a baseline of expected functionality and the gaps to be filled; and constraints imposed by the operating environment, namely the prevalence of mobile money, the cost and instability of bandwidth, the predominance of mobile devices, and the official bilingualism of Cameroon.

Methodological limitation

Requirements were not elicited through a formal structured instrument such as a distributed questionnaire or recorded interview programme, and no statistical characterisation of the user population was produced. The requirements presented below are therefore reasoned rather than surveyed. This is a genuine weakness of the methodology and is revisited in Section 6.6 and Section 8.2.

Chapter Four

System Design

4.1  Architectural design

The system adopts a three-layer client–server architecture with the presentation layer deployed independently of the application layer. The separation is deliberate: static assets benefit from content-delivery distribution, whereas the application layer must hold long-lived WebSocket connections and run a background scheduler. These have incompatible hosting profiles, and the accepted cost of separating them is that the two tiers occupy different origins, making cross-origin policy a first-class design concern (Section 5.1).

4.1.1  Request pipeline

Every authenticated request traverses a fixed middleware sequence. Ordering is significant and is enforced in the application entry point:

Request
  -> trust proxy          resolve true client address and protocol behind the host proxy
  -> HTTPS redirect       308, preserving method and body on non-GET requests
  -> security headers     CSP, HSTS, nosniff, frame-ancestors none
  -> CORS                 explicit origin allow-list; wildcard impermissible with credentials
  -> body parser          JSON, limited to 1 MB
  -> rate limiter         selected by path
  -> authenticate         verify token, populate request identity
  -> authorise            role check, re-read from database
  -> handler              Prisma query, response
  -> error handler        log fully, return generic message

4.3.1  Design decisions in the data model

  • Votes as entities. Recording each vote as a row with a uniqueness constraint on voter and target makes repeat voting impossible at the storage layer. An integer counter would have pushed that guarantee into application code, where any path that forgets the check defeats it.
  • Soft deletion of messages. A deleted message retains its row and is flagged, so the interface renders a placeholder rather than removing it. This preserves the coherence of a conversation others have already replied to.
  • Entitlement as a record, not a flag. Access to paid content is determined by the existence of a purchased_notes row rather than a boolean, yielding an auditable record of who purchased what and when.
  • Trust computed, not stored. Permission to publish paid material without review is derived at query time from recent review history. A stored flag requires something to remember to revoke it; a derived one lapses automatically when the history no longer supports it.

4.3.2  Connection strategy

The datasource declares two connection strings. The application uses a pooled endpoint, keeping concurrent connections within the limits of the hosting tier. Migrations use a direct endpoint, because the pooler operates in transaction mode and cannot carry the session-scoped advisory locks and type-creation statements that migrations require. Routing migrations through the pooled endpoint produces a failure whose message does not identify pooling as the cause, which is recorded here because it cost material debugging time.

Two invariants this design protects

Price integrity. The client never transmits an amount. Every charge is resolved from the database when the transaction is created, so a modified request cannot alter what is charged.

Exactly-once granting. The browser poll and the reconciler may observe success concurrently. Granting is therefore performed through a conditional status update, so exactly one of the racing callers performs the grant and the other observes that it has already occurred.

4.5  Interface design

The interface is built on a token-based design system rather than per-page styling. One stylesheet defines a brand scale, neutral surfaces, semantic status colours, elevation and radii as CSS custom properties. Tailwind's @theme inline directive exposes these as utility classes that retain a var() reference instead of compiling to a fixed value, which is what permits the light and dark themes to switch at runtime by changing a single attribute on the document root, with no rebuild and no flash of restyled content.

Seventeen shared primitives implement every recurring visual element. Consolidating them replaced a situation in which the same component — a button, a modal, a status badge — had been implemented separately on each page and had drifted apart visually. Contrast ratios in both themes were chosen to satisfy NFR-09, which required separating the accent colour used for text from the one used as a fill behind white text, since a single value cannot satisfy both the 4.5:1 and 3:1 thresholds simultaneously.

The layout is mobile-first throughout, in recognition that the majority of the intended users will access the platform on a handset over a metered connection.

Chapter Five

Implementation

This chapter documents how each subsystem was realised, concentrating on decisions whose rationale is not evident from the code alone.

5.1  Authentication and authorisation

Passwords are hashed with bcrypt at a work factor of twelve, satisfying NFR-01. Authentication issues a JSON Web Token carrying the user identifier, signed with a server-held secret and expiring after twenty-four hours. The client stores the token and attaches it to every request through an interceptor, so no call site handles the header individually.

Two details in the login path are worth recording. First, a bcrypt comparison is executed even when the submitted email matches no account, comparing against a discarded dummy hash. Without this, a non-existent account returns measurably faster than an incorrect password, permitting an attacker to enumerate registered addresses by timing alone. Second, role checks re-read the role from the database rather than trusting the claim embedded in the token, so that a revoked administrator loses access immediately instead of at token expiry.

Three authorisation middlewares are provided. authenticate requires a valid token. optionalAuth populates the identity when a token is present but never rejects, serving endpoints that are public yet render differently for a signed-in user — for instance, indicating whether the viewer already owns a paid note. requireRole is a factory enforcing one or more roles. The WebSocket handshake reuses the same verification, and group membership is checked against the database before a socket is admitted to a room, so room membership cannot be asserted by the client.

Because the two tiers occupy different origins, cross-origin policy is load-bearing rather than incidental. Origins are supplied by configuration as an explicit allow-list; a wildcard is impermissible because credentials are enabled. Two diagnostics were added after misconfiguration proved difficult to trace: a rejected origin is logged by name alongside the allow-list, exposing a trailing slash or scheme mismatch that is otherwise invisible; and a production server booting with only a local origin configured prints a prominent startup error, because that state rejects every browser request with an opaque status that presents as a client-side defect.

5.2  Collaboration subsystem

Group messaging is delivered over Socket.IO, with one room per group. The server emits events for new messages, edits, deletions, reactions, typing state and presence. Message sending is optimistic: the message appears immediately in the sender's view marked as pending and is replaced when the server's copy arrives. The echo of the sender's own message is suppressed, since otherwise the author would see it twice.

A polling fallback is retained but deliberately subordinated. When the socket is connected the client polls every thirty seconds; when it is not, every four. The poll exists to repair events missed during a brief disconnection, not to drive the conversation. This matters on an unstable connection, where a socket may drop without the client observing a clean close.

Message editing is permitted within fifteen minutes of posting. Deletion is soft, as described in Section 4.3.1, and may be performed by the author or by a group administrator acting as moderator.

5.3  Content subsystem and access control

Uploads are parsed by Multer and streamed directly to Cloudinary without touching the application's filesystem, which is necessary because the hosting platform provides an ephemeral disk that is discarded on every redeployment. Files are constrained to 20 MB and validated against a MIME allow-list.

Delivery differs by whether the content is protected, and this distinction produced the single largest measured performance improvement in the project:

  • Free content is not proxied. The server responds with a redirect to the content-delivery URL, so the file is served by the CDN rather than streamed through a constrained application process.
  • Paid content is uploaded under Cloudinary's authenticated delivery type, which is not retrievable from a plain URL. After confirming that an entitlement record exists for the requesting user and the requested note, the server issues a short-lived signed URL. Legacy files held locally are stored beneath a directory that the static middleware refuses outright, so the only route to them is through the entitlement check.
Measured outcome (NFR-11)

Before the redirect was introduced, a 3.19 MB PDF proxied through the application server did not complete within the 300-second client timeout. After the change, the same file on the same connection was delivered in 31 seconds. The improvement is attributable to removing a constrained single process from the data path, not to any change in the file.

5.4  Tutoring and payment subsystem

All provider interaction is confined to a single adapter module, so that no route communicates with the payment SDK directly. The adapter normalises telephone numbers to a nine-digit local form, accepting the international and spaced variants students actually type; detects the operator from the prefix and rejects a mismatch between the detected operator and the selected service before any request is issued; and requests collection in asynchronous mode so the HTTP call returns immediately rather than blocking for the duration of the subscriber's interaction with the prompt.

Cancellation is not a local state change. When a payer abandons a payment, the server first interrogates the provider, because settlement may have completed between the decision to cancel and the arrival of the request. A reported success completes the order and grants access; a reported failure marks the transaction failed; an absent reference cancels, nothing having been charged; and a still-pending state is left pending and handed to the reconciler, with the user informed that confirmation is continuing. Without this, a user who cancelled a fraction of a second after approving would have been charged and left without access.

Defect discovered during integration

The provider authenticates each request with a signature computed over the serialised request body. Any character above U+007F in that body causes rejection with a message indicating a bad signature — an error that directs attention to the credentials rather than to the payload. A single typographic dash in a note title was sufficient to break every purchase of that note while purchases of other notes continued to succeed, which made the fault appear intermittent and unrelated to content.

The resolution was a sanitising helper in the adapter that folds typographic punctuation to ASCII equivalents, removes any remaining character above U+007F, collapses whitespace and truncates to 120 characters. Every field transmitted to the provider passes through it. The episode is recorded because the initial diagnosis was wrong: the credentials were suspected first, and a diagnostic endpoint had to be written to establish that the deployed keys were byte-identical to the working local ones before attention moved to the payload.

5.5  Quality gate and moderation

Charging for content creates an obligation to ensure it is worth paying for. Two mechanisms operate in sequence.

An automated gate examines each paid upload, extracting text from PDF documents by decompressing the relevant content streams and reading the text-showing operators, then measuring word count, page count, byte size and lexical variety. Variety is computed as a type-to-token ratio averaged over fixed windows rather than across the whole document, because an unwindowed ratio falls as length rises and would therefore penalise long documents purely for being long.

The scope of this gate is deliberately limited, and the limitation is documented in the source. No heuristic can distinguish a correct derivation from a confidently incorrect one. What the gate detects is material that is obviously unfit for sale: near-empty files, placeholder text, padding and unreadable scans. Correctness is the province of the human review queue, and the automated stage exists only to keep the obviously unfit from reaching it.

Human review is performed by an administrator, who must open and read the file before deciding. A rejection requires a written reason, which is transmitted to the author, on the principle that a rejection without an actionable explanation merely wastes the contributor's effort. Contributors with an established record bypass the queue, using the computed trust rule described in Section 4.3.1: at least three approvals and no rejections within the last ten reviewed uploads.

5.6  Internationalisation

The interface is fully available in English and French, with 1,228 translation keys in each language, satisfying NFR-10. Language is detected in the order stored preference, then browser setting, then document attribute. A stored choice deliberately takes precedence over the browser, since a user who has explicitly selected a language should not have that selection overridden on a subsequent visit. Regional variants are mapped onto the base language, so that a browser reporting fr-CM resolves to French; without this mapping, Cameroonian browsers reporting a region would silently have received English, which is precisely the population the requirement exists to serve.

The governing implementation rule is that values which are stored or searched remain in English, and only their displayed labels are translated. Subjects, fields of study, availability days, question categories and booking statuses are all persisted. Translating the stored value would mean that a French-speaking tutor's subject never matched an English-speaking student's search for the same subject, and the two would silently fail to find one another.

Several consequences of this rule required specific handling. Plural forms are expressed through the internationalisation library's plural categories rather than by appending a character, because French pluralisation does not follow the English pattern. Dates and numbers are formatted in the active locale. The account-deletion confirmation compares typed input against the translated word, since translating only the visible instruction would have left French users typing the French word at a permanently disabled button. Transient notification text is resolved from the library instance rather than the React hook, which keeps the translation function out of data-fetching closures and their dependency arrays.

A consistency checker was written to prevent the two locale files from diverging as the application grows. It fails the build on four conditions: a key present in one language but absent from the other, differing interpolation placeholders between languages, a plural family missing a required form, and a key referenced in code but defined nowhere. It also reports keys identical in both languages and keys nothing references, without failing, since both are usually legitimate but merit inspection. Its value was demonstrated immediately, as described in Section 6.5.

5.7  Resilience and offline capability

The hosting tier suspends the application server after approximately fifteen minutes without traffic, and the first request to reach a suspended instance is typically lost while the container starts. Untreated, a visitor arriving from a shared link encounters a failure on an entirely healthy service.

The client therefore retries, but narrowly. Only requests that received no response whatsoever are retried, at most twice and four seconds apart. Any request the server actually answered — including one answered with a server error — is not retried, because repeating a request the server did process risks duplicating its effect. While a retry is outstanding the client displays an explanatory banner, so the delay is accounted for rather than silent. This satisfies NFR-08.

The application is installable as a Progressive Web Application, satisfying NFR-13. Its service worker applies caching strategies chosen per resource class rather than uniformly: public statistics are served stale while revalidating; listings of groups, notes and questions prefer the network but fall back to cache, making them readable offline; and authentication, payment, messaging and tutor rates are never cached, because serving any of those from a stale copy would be actively harmful.

Chapter Six

Testing and Validation

6.1  Testing strategy

Validation combined four techniques: continuous static analysis, production build validation as a compilation gate, a purpose-written automated consistency checker, and structured manual functional testing. The strategy and its principal weakness are stated plainly below.

Principal weakness of the strategy

The project does not include an automated regression test suite. There is no unit, integration or end-to-end test framework configured, and no test runner in either package manifest. Verification of behaviour was performed by ad-hoc scripts written to exercise a specific change and by manual execution of test cases; the scripts were not retained as a maintained suite. Consequently there is no automated protection against regression, and every change is re-verified by hand. This is the most significant deficiency of the work and is the first recommendation in Section 8.3.

6.2  Static analysis and build validation

ESLint runs across the client source with the React Hooks and React Refresh rule sets enabled. The codebase carries a known baseline of 42 errors and 13 warnings, predominantly effect-ordering advisories and unused bindings. The baseline was not eliminated; instead the working rule adopted was that no change may increase either count, which converts the tool into a usable regression signal despite the outstanding debt.

The production build is treated as the authoritative gate rather than the development server. This is a consequence of the styling approach: a mistyped design token resolves silently in development but fails the production build, so a change that runs correctly under the development server is not thereby validated.

6.3  Automated consistency checking

A checker was written to enforce internal consistency between the two locale files, invoked through a package script. It fails on four conditions, each of which would otherwise reach production as visibly incorrect text:

6.6  Threats to validity

  • No formal user evaluation. No usability study, questionnaire or controlled trial was conducted with the intended student population. Claims about usability rest on adherence to accepted design criteria such as WCAG contrast thresholds, not on measured user performance or reported satisfaction. No claim of demonstrated user acceptance is made anywhere in this report.
  • Single-operator testing. Payment flows were exercised with a live MTN Mobile Money account. The Orange Money path shares the same adapter, normalisation and settlement logic and differs only in the operator identifier transmitted, but it was not exercised end-to-end with a live Orange subscription. It is therefore verified by construction rather than by observation.
  • No load testing. The system has not been subjected to concurrent load. Statements about scalability are architectural arguments, not measurements.
  • Single-tester bias. All manual testing was performed by the developer, who knows the intended paths. This systematically under-samples the unexpected sequences that unfamiliar users generate.
  • Limited device coverage. Responsive behaviour was verified by viewport emulation and on a limited set of physical devices, not across the range of handsets in actual use.

7.3  Discussion of design decisions

Treating the browser as an observer of payment. The most consequential decision in the system was to deny the client any authority over payment outcomes. A design in which the browser reports success, or in which the poll is the sole settlement path, is simpler and works under demonstration conditions. It fails in exactly the circumstances the target users experience most often: a dropped connection, a closed tab, a PIN entered after a delay. Moving the authority to a server-side reconciler cost additional complexity and a background process, and it is the reason a student who loses signal mid-payment still receives what they paid for.

Computing trust rather than storing it. Deriving publication privileges from recent review history, instead of persisting a flag, eliminates a class of failure in which a privilege outlives the conduct that justified it. The general principle — that derived state cannot drift out of step with the facts it is derived from, whereas stored state requires discipline to maintain — applied in several places in the design.

Separating stored values from displayed labels. The internationalisation rule that persisted values remain in English proved more consequential than anticipated. It is the difference between a bilingual interface and a partitioned platform in which francophone and anglophone users cannot find one another's content. The failure mode would have been silent: no error, simply empty search results for some pairs of users.

Designing against WhatsApp rather than against web platforms. Because the incumbent is a free, universally installed messaging application, the acceptance threshold is set by it rather than by comparable web systems. This justified investment in installability, offline tolerance and first-load behaviour that would be difficult to defend against a purely feature-based comparison.

7.4  Constraints imposed by context

Several characteristics of the delivered system are direct consequences of operating on free-tier infrastructure, and would not be present in a resourced deployment. The application server suspends when idle, necessitating the retry and notification behaviour of Section 5.7. Connection pooling limits dictated the dual database connection strategy of Section 4.3.2. The ephemeral filesystem of the hosting platform required that all uploads be externalised, which in turn made the CDN redirect of Section 5.3 both possible and necessary. These are not design preferences; they are adaptations, and they are documented as such so that a future maintainer does not mistake them for arbitrary complexity and remove them.

Chapter Eight

Conclusion and Future Work

8.1  Conclusion

This project set out to address the absence of a single accessible platform on which university students could share academic resources, resolve specific difficulties and obtain paid peer tutoring, using payment instruments appropriate to the Cameroonian context. A full-stack web application meeting that description was designed, implemented and publicly deployed.

Eight of the nine stated objectives were achieved in full and the ninth in part, the shortfall being the absence of a formal user evaluation rather than any deficiency in the delivered functionality. The system integrates four capabilities that are elsewhere available only separately — collaborative groups, a shared content repository, a reputation-bearing question forum, and a tutoring marketplace — and settles payment through the mobile money instruments the intended users actually hold.

Beyond the functional result, the project produced engineering outcomes of wider applicability. The payment design demonstrates that reliable entitlement granting over an asynchronous and unreliable settlement rail is achievable through server-side price resolution, idempotent granting and background reconciliation, without requiring the client to remain connected. The content-delivery design shows that protected digital goods can be served securely from constrained infrastructure by separating the authorisation decision from the byte delivery, with a measured order-of-magnitude improvement in transfer time for unprotected content. The internationalisation work establishes a rule — that persisted values remain canonical while only labels are translated — whose violation would have silently partitioned the user base along linguistic lines.

The project also illustrates, through the defect record of Table 6.3, the practical value of mechanical verification. Every fault for which an automated check existed was caught before deployment; every fault that reached a user-visible state did so in an area where no such check existed.

8.2  Limitations

The following limitations are stated so that the results are not read as claiming more than was demonstrated.

Methodological

  • Requirements were reasoned from observation and comparative analysis rather than elicited through a formal instrument administered to the user population.
  • No user evaluation was conducted; no claim of measured usability or user acceptance is made.
  • All testing was performed by the developer, with the sampling bias that implies.

Technical

  • There is no automated regression test suite.
  • Sessions are stateless tokens, so a token remains valid until expiry even after sign-out or suspension. A short lifetime bounds the exposure; it does not remove it.
  • The static analysis baseline of 42 errors was held constant rather than eliminated.
  • The system has not been load tested; scalability claims are architectural rather than measured.
  • The Orange Money path is verified by construction rather than by live end-to-end execution.

Functional

  • Direct messaging to a tutor persists to browser storage only and is not transmitted; the feature is present in the interface but not functional end-to-end.
  • Session resource downloads on the tutor profile are simulated rather than served.
  • Notification preferences in settings are not persisted.
  • Email notification is not implemented; notifications are in-application only.
  • Server-composed text — notification bodies, certain payment messages and the rendered receipt — remains English-only, so translation coverage is complete for the interface but not for the system as a whole.
  • Two landing-page figures are placeholder values rather than measured statistics and should be connected to the live counters or removed before further promotion.

Deployment caution

Client variables are compiled into the bundle at build time rather than read at run time. Altering one in a hosting dashboard has no effect until the project is rebuilt. An incorrect API address therefore produces a client that loads perfectly and then fails every request, presenting as a server outage when it is a build configuration fault.
